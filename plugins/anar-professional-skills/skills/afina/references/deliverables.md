# Результаты и передача Афины

Выбирай форму по риску и объёму изменения. Для Quick достаточно нескольких абзацев; для Standard — связанного среза сценария. Для Deep раскрывай критические зависимости и проверку, не заполняя неприменимые разделы.

## UX Architecture Note

При необходимости собери: проблему и outcome; факты/допущения; роли и критический путь; IA и язык объектов; карту экранов; состояния и переходы; решения и defaults; Screen Contracts; системные зависимости; существенные развилки с рекомендацией; проверку и следующий шаг. Карта или таблица нужны, если делают связи яснее. Целевой эмоциональный результат может быть гипотезой, но не критерием доказанного успеха без наблюдений.

## Единый Screen Contract и пакет передачи Зевсу

Контракт должен быть пригоден к передаче сам по себе. Общие ограничения можно вынести в точно указанную доступную зависимость с версией; не оставляй важные условия только в истории разговора. Ниже шаблон для отбора применимых полей, а не обязательная форма каждой задачи.

```yaml
screen: <название и границы изменения>
outcome: <что человек должен понять или сделать>
role_and_context: <роль, права, рабочая ситуация>
scenario: <вход → здесь → выход; куда возвращается контекст>
primary_action: <действие или отсутствие действия у обзорного экрана>
required_information:
  - <смысл, единицы, период, источник, свежесть по применимости>
restricted_information:
  - <что нельзя раскрыть данной роли; системное основание>
decisions_and_defaults:
  - <кто решает, какое умолчание, почему и как изменить>
states_and_priority:
  - <состояние → обязательный смысл → приоритет при сочетании>
error_and_recovery:
  - <отказ/прерывание → последствия → сохранность → продолжение>
invariants_and_dependencies:
  - <правило; evidence или непроверенная зависимость>
platform_and_accessibility:
  - <платформа, управление, фокус, сообщения, критерии>
visual_freedom: <что Зевс выбирает самостоятельно>
acceptance:
  - <наблюдаемые сценарии и ожидаемые результаты>
verification:
  - <выполненная проверка → evidence → предел вывода>
open_questions:
  - <существенный вопрос → владелец → что именно заблокировано>
next_action: <получатель, конкретный первый шаг>
```

Афина определяет смысл, состав информации, порядок действий и приоритет состояний. Зевс определяет визуальную иерархию, композицию, типографику, компоненты и оформление. Например, Афина требует, чтобы неопределённая сумма не выглядела подтверждённым нулём; Зевс выбирает её конкретное визуальное выражение. Не предписывай палитру и декоративное решение без отдельного принятого ограничения.

При передаче укажи фактические артефакты, текущие решения, основания и статус готовности. Не передавай критическое UX-решение как «дизайнер разберётся». Если Зевс обнаружил потерю сценария или системную невозможность, согласуй затронутую часть контракта, затем перепроверь зависимые переходы. Афина не проводит параллельный Visual Loop по собственному вкусу.

## Проверка и статус готовности

Для каждой существенной проверки: объект и условия → метод → наблюдение/ссылка → вывод → предел/следующий шаг.

| Проверка | Что установить |
|---|---|
| Scenario / navigation | Достижение цели; вход/выход, возврат, другая роль, сохранение контекста, отсутствие тупика |
| State / data | Различение loading, empty, zero, error, partial, stale, restricted, success; приоритет конкурирующих состояний |
| Error / recovery | Предотвращение ошибки; последствия, сохранность, повтор, отмена/исправление согласно системным гарантиям |
| Accessibility | Путь с клавиатурой и иными средствами управления, фокус, понятные названия, ошибки и status messages; конкретные применимые критерии |
| Business / feasibility | Не искажены суммы, период, статусы, роли, доступ, транзакции; backend исполняет обещаемое |
| Visual / runtime | Доступный дизайн или фактический интерфейс сохраняет контракт; не замена пользовательской валидации |
| User / outcome | Понимание и выполнение задачи в указанных условиях; замеры эффекта отдельно от прогноза |

Если значимая проверка недоступна, напиши «не выполнено: причина → что и как проверить». Не заявляй соответствие WCAG всего продукта по одному экрану или одной эвристике. Типы свидетельств и пределы выводов определены в `SKILL.md`.

Различай статусы: **UX-контракт готов**, **реализация проверена**, **гипотеза поддержана наблюдениями**, **эффект измерен**, **зависимая часть заблокирована**. Они могут относиться к разным частям одной задачи. Нельзя превращать отсутствие прототипа в утверждение об удобстве, а отсутствие runtime-доступа — в ложный положительный результат.
