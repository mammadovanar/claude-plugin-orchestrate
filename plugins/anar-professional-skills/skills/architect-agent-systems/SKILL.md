# Архитектор агентных систем

Проектировать не набор промптов, а управляемую производственную систему:

`Источники → протоколы → навыки → агенты → оркестратор → состояние и обучение`.

Сохранять ядро коротким. Кодировать механизм выбора и границы ответственности, а не пытаться перечислить все будущие случаи.

Использовать Loop как поперечный механизм автономности: он связывает действие, проверку, обратную связь и следующий улучшенный проход внутри нужного слоя системы.

## Процесс

### 1. Восстановить замысел

Собрать из запроса и доступных артефактов:

- результат, ради которого существует система;
- уже существующие агенты, навыки, процессы и память;
- повторяющиеся решения и явные запреты;
- текущие сбои: пробел, дублирование, конфликт полномочий или чрезмерный процесс.

Не начинать проектирование новой роли, пока не проверено, нельзя ли закрыть потребность изменением существующего владельца, навыка или контракта.

### 2. Определить правильный слой

Размещать новую логику на минимально достаточном уровне:

| Если требуется | Создавать или менять |
| --- | --- |
| Метод мышления из источника | Протокол |
| Автоматически вызываемая повторяемая процедура | Навык |
| Владелец цели, решений и результата в одной профессии | Агент |
| Маршрутизация, последовательность, барьеры и состояние | Оркестратор |
| Накопление проверенных уроков между запусками | Память / state |

Не помещать оркестрацию внутрь каждого агента и не превращать навык в персонажа.

### 3. Выбрать вес процесса

Классифицировать задачу через Cynefin как короткий фильтр, затем оценить стоимость ошибки, обратимость, связанность, неопределённость, проверяемость и наблюдаемость.

- **Express** — очевидное, локальное, обратимое изменение; один исполнитель, необходимые проверки, короткий handoff.
- **Linear** — связанная задача с одним основным потоком; framing → владелец → реализация → независимая проверка → выпуск.
- **Parallel** — действительно независимые части с явными контрактами; отдельные владельцы и рабочие области, затем барьер интеграции.
- **Discovery** — запутанная или новая область; сначала исследование, эксперименты и сужение неопределённости, затем обязательная повторная классификация.

Предпочитать Linear. Параллелить только независимую работу, а не неопределённость.

### 4. Выявить и спроектировать Loop

Искать Loop там, где результат нельзя получить одним проходом: проверка меняет следующее решение, артефакт уточняется по обратной связи или система должна самостоятельно исправлять отклонение от цели.

Не путать Loop с программным циклом или заранее заданным чеклистом. Loop задаёт агенту **цель, рамку мышления и способ учиться на результате**, оставляя свободу найти путь.

Для каждого Loop зафиксировать:

`цель → наблюдение → решение → действие → проверка факта → извлечение обратной связи → следующий изменённый проход`.

Определить владельца, изменяемое состояние, критерий прогресса, критерий завершения, retry/time/risk budget и условие эскалации. Новый проход обязан менять гипотезу, действие или контекст; механическое повторение не является Loop.

Различать внешний Loop, который улучшает итоговый продукт или решение, и внутренние Loop отдельных ремёсел. Внутренний Loop не может изменить цель внешнего контура без явного handoff владельцу цели.

### 5. Извлечь механизмы из библиотеки

Выбрать один главный источник и не более двух вспомогательных. Для каждого:

1. назвать проблему, которую он помогает решить;
2. извлечь конкретный механизм;
3. проверить применимость к текущему контексту;
4. встроить механизм в решение;
5. показать, какое решение из-за него изменилось.

Использовать источник только если его механизм повлиял на решение. Не перечислять книги как украшение. Подробную карту устойчивых механизмов читать в [method.md](references/method.md), когда нужна библиотека или выбор протокола.

### 6. Спроектировать контракты

Для каждого компонента зафиксировать:

- trigger и вход;
- единственного владельца решения;
- границы роли и запреты;
- выходной артефакт;
- критерии готовности и проверку факта;
- следующий владелец и handoff;
- stop/escalation conditions;
- правила чтения и обновления состояния.
- Loop-контракт, если результат требует итеративного поиска или самокоррекции.

Соблюдать инварианты: автор ≠ независимый reviewer; reviewer ≠ release owner; один результат — один явный владелец. Не давать нескольким авторам писать в одну рабочую область параллельно.

### 7. Сформировать тонкое ядро

Для агента использовать формулу:

`имя → профессия → главная сила → миссия → границы → способ мышления → библиотека → рабочий Loop → execution mode → проверка → handoff`.

Для навыка оставлять только trigger, решение о маршруте, обязательный процесс, Loop при его наличии, контракты и проверку. Варианты, шаблоны и подробности выносить в references. Для оркестратора задавать стадии, режимы, ownership, Loop-контуры, барьеры, состояние и восстановление после остановки.

Читать [templates.md](references/templates.md) при создании конкретного агента, навыка или оркестратора.

### 8. Провести проверку системы

Проверить как минимум три сценария:

- типичный запрос;
- пограничный запрос, где роли или навыки могут пересечься;
- рискованный запрос, где система должна усилить контроль или остановиться.

Оценивать не красоту текста, а наблюдаемое поведение: правильный trigger, выбор владельца, отсутствие дублей, минимальный достаточный процесс, качественный артефакт, осмысленное изменение между проходами Loop, независимая проверка и корректный handoff.

Читать [validation.md](references/validation.md) перед финализацией сложной или многоагентной системы.

## Формат результата

Возвращать:

1. **Диагноз** — что именно отсутствует или конфликтует.
2. **Архитектурное решение** — какой слой меняется и почему.
3. **Карта системы** — компоненты, владельцы и поток артефактов.
4. **Готовые артефакты** — промпты, SKILL.md, контракты или патчи.
5. **Проверка** — сценарии, доказательства и оставшиеся риски.

Не раздувать результат объяснениями, которые не меняют реализацию.
