# Повторяющийся метод

## Каноническая модель

### Источники

Книги, стандарты, исследования, документация и проверенный опыт. Источник не управляет выполнением напрямую.

### Протоколы

Операционализированные механизмы из источников: диагностировать, классифицировать, декомпозировать, проверить или принять решение. Протокол должен менять действие, а не добавлять авторитетную ссылку.

### Навыки

Автоматически вызываемые специализированные процедуры. Навык распознаёт форму задачи, выбирает подходящий протокол, производит определённый артефакт и проверяет его.

### Агенты

Узкие профессиональные владельцы результата. Агент понимает цель, принимает решения внутри своей компетенции, применяет навыки, работает с инструментами и отдаёт проверяемый handoff. Персонаж помогает удержать ремесло и приоритеты, но не заменяет контракт роли.

### Оркестратор

Единый дирижёр процесса. Он выбирает режим, назначает ownership, управляет стадиями и состоянием, предотвращает конфликт авторов, проводит через барьеры и возобновляет работу после остановки. Оркестратор не должен подменять профессиональное решение агента.

### Память и state

Хранят не весь след рассуждений, а решения, ограничения, доказательства, текущую стадию, владельца, незакрытые риски и проверенные уроки. Состояние должно позволять продолжить процесс без повторного изобретения задачи.

## Устойчивая логика выбора

1. **Cynefin** — определить природу ситуации и допустимый способ продвижения. Не пересказывать фреймворк; использовать его для выбора режима.
2. **Good Strategy / Bad Strategy** — сформировать диагноз, направляющий подход и согласованные действия. Не подменять диагноз списком симптомов.
3. **Software Engineering at Google** — формировать изменение как долговечную инженерную единицу: ясный владелец, малый reviewable scope, проверяемость, сопровождаемость и обучение процесса.
4. **Are Your Lights On? / problem framing** — проверить, решается ли правильная проблема и для кого она является проблемой.
5. **Доменные источники** — выбирать после классификации: архитектура, данные, UX, безопасность, надёжность и другие только по природе задачи.

Порядок: `классифицировать → выбрать 1+до 2 источников → извлечь механизм → проверить применимость → применить → верифицировать`.

## Принципы построения системы

### Изменение раньше агента

Сначала определить форму изменения и требуемый артефакт, затем назначить агента. Иначе роли начинают диктовать архитектуру задачи.

### Один владелец решения

У каждого этапа и артефакта должен быть один accountable owner. Участников может быть несколько, но право финального решения на этапе не размывается.

### Разделение полномочий

Автор создаёт. Reviewer независимо ищет ошибки и подтверждает критерии. Release owner интегрирует и выпускает. Совмещение допустимо только в Express для низкого риска и должно быть явным.

### Процесс пропорционален риску

Вес процесса определяется свойствами изменения, а не названием задачи или фиксированным ритуалом. Критические данные, деньги, пользователи, безопасность, tenants, заказы, платежи, миграции, внешние API и production повышают необходимую глубину.

### Минимальные проверяемые изменения

Декомпозировать на части, которые можно понять, проверить и при необходимости откатить независимо. Декомпозиция нужна не только для параллельности.

### Контракты вместо телепатии

Передавать артефакт, решение, доказательства, ограничения, открытые риски и следующий шаг. Не считать историю чата достаточным handoff.

### Обучение замыкает контур

После выпуска отделить локальную случайность от повторяемого урока. Обновлять навык или процесс только проверенным обобщением, а не единичным предпочтением.

## Loop как механизм автономного поиска

Loop — это управляемый контур самокоррекции, а не повтор команды. Он нужен, когда следующий ход нельзя полностью определить заранее: его выбирают по результату предыдущего действия.

### Как выявить Loop

Проверить процесс на признаки:

- результат одного прохода становится доказательством для следующего решения;
- проверка может вернуть артефакт владельцу на содержательную доработку;
- цель стабильна, но путь уточняется через действие и наблюдение;
- агент должен сравнивать намерение, план и факт;
- повторяемые решения могут сформировать проверенный урок для будущих запусков.

Если следующий шаг заранее известен и не зависит от обратной связи, это sequence. Если выбирается один из заранее известных путей, это branch. Если обратная связь меняет новый проход, это Loop.

### Контракт Loop

1. **Goal** — наблюдаемое состояние, ради которого работает контур.
2. **Frame** — профессиональная рамка и инварианты, ограничивающие поиск.
3. **Observe** — факты о текущем состоянии, а не впечатление агента.
4. **Decide / Act** — гипотеза и минимальное действие, способное дать новую информацию или приблизить цель.
5. **Verify** — сравнение результата с критерием.
6. **Learn** — что изменилось в модели задачи и что поэтому делать иначе.
7. **Continue / Exit / Escalate** — следующий изменённый проход, завершение или передача блокера.

### Вложенные контуры

Использовать Outer Loop для движения к пользовательскому или продуктовому результату. Использовать Inner Loop для качества отдельного ремесла: архитектуры, UX, визуального дизайна, реализации, отладки или review. Inner Loop улучшает свой артефакт внутри контракта Outer Loop и возвращает доказательства наружу.

Не разрешать внутреннему контуру незаметно менять цель, scope или инварианты внешнего. Такие изменения требуют возврата к владельцу Outer Loop.

### Управление автономностью

Продолжать Loop до достижения критерия, реального блокера или исчерпания бюджета. Фиксировать после прохода текущее состояние, проверку, новую информацию и следующий выбор, чтобы процесс можно было возобновить.

Останавливать Loop, если:

- новый проход не меняет гипотезу, действие или доступные данные;
- две правки циклически отменяют друг друга;
- нет наблюдаемого прогресса за установленное число попыток;
- продолжение требует нового полномочия или необратимого решения;
- цена следующего эксперимента превышает согласованный риск.

После остановки не повторять попытку под другим названием: сузить проблему, получить новые данные, изменить рамку либо эскалировать.

## Канонический поток изменения

`Change request → framing → sizing → ownership → specification при необходимости → implementation → presubmit → independent review → integration → release → learning`.

Спецификация включается по неопределённости и риску, а не как обязательный документ на каждую мелочь. Нельзя отдавать неоднозначную критичную задачу в реализацию без достаточного контракта.

## Антипаттерны

- длинный список правил вместо механизма выбора;
- новая роль для каждого нового кейса;
- одинаковые полномочия у нескольких агентов;
- книги, которые названы, но ничего не изменили;
- параллельные авторы в одной рабочей области;
- review собственных решений под видом независимой проверки;
- гигантская спецификация, не разбитая на reviewable changes;
- оркестратор, который пишет всё сам;
- память как свалка полного лога;
- Loop без цели, изменяемой обратной связи, бюджета или выхода;
- повтор одной и той же попытки под видом автономности;
- автоматическое продолжение через необратимое решение пользователя;
- перенос legacy-домена в новое ядро без повторного исследования.
