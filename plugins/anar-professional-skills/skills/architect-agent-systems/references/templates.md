# Шаблоны проектирования

Использовать как каркас, удаляя неприменимые секции. Не заполнять их общими словами.

## Агент

```markdown
---
name: <имя>
description: <профессия, конкретный trigger и результат>
tools: <только необходимые инструменты>
---

# <Имя> — <профессия>

## Миссия
<один принадлежащий агенту результат>

## Главная сила
<что этот агент делает лучше остальных>

## Границы
- Делает: ...
- Не делает: ...
- Передаёт: ...

## Решение
1. Диагностировать ...
2. Выбрать глубину по ...
3. Применить механизм ...
4. Создать артефакт ...
5. Проверить факт ...

## Библиотека
<источник → проблема → извлекаемый механизм>

## Execution mode
<автономия, инструменты, остановки, эскалация>

## Handoff
<кому, что, в каком формате и с какими доказательствами>
```

## Навык

```markdown
---
name: <verb-led-name>
description: <что делает + все условия автоматического вызова>
---

# <Название>

## Маршрутизация
<как распознать форму задачи и выбрать вариант>

## Процесс
1. <обязательное действие>
2. <решение, зависящее от контекста>
3. <создание результата>
4. <проверка>

## Контракт результата
<обязательные поля или артефакты>

## Ограничения
<запреты, stop conditions, ownership>

## References
<что читать и только при каком варианте>
```

## Оркестратор

```markdown
# Цель процесса
<какой результат доводится до готовности>

## Вход
<change request и обязательный контекст>

## Выбор режима
- Express: ...
- Linear: ...
- Parallel: ...
- Discovery: ...

## Стадии
| Стадия | Владелец | Вход | Выход | Gate |
| --- | --- | --- | --- | --- |
| Framing | ... | ... | ... | ... |

## Инварианты
<разделение ролей, рабочие области, prod-права>

## State
<что фиксируется после каждой стадии>

## Resume
<как определить последнюю подтверждённую стадию и продолжить>

## Stop / escalation
<необратимость, нехватка полномочий, пользовательская развилка>

## Learning
<как проверенный урок обновляет систему>
```

## Loop-контракт

```markdown
## <Название> Loop

- Goal: <наблюдаемое состояние результата>
- Frame: <профессиональная рамка и инварианты>
- Owner: <кто принимает решение о следующем проходе>
- State: <что переносится между проходами>
- Observe: <какие факты считываются>
- Act: <какое минимальное изменение или эксперимент допустим>
- Verify: <как результат сравнивается с целью>
- Learn: <что обязано измениться в следующем решении>
- Progress signal: <наблюдаемый признак продвижения>
- Exit: <критерий готовности>
- Budget: <число попыток, время, стоимость или риск>
- Escalate: <блокер или решение за пределами полномочий>
```

При вложенных контурах дополнительно указать, какой Outer Loop задаёт цель и какой артефакт Inner Loop обязан вернуть наружу. Не создавать Loop, если достаточно sequence или branch.

## Handoff

```yaml
handoff_schema: 1
change: <идентификатор и цель>
stage: <завершённая стадия>
owner: <автор результата>
artifact: <путь или точное содержание>
decisions:
  - <решение и причина>
verification:
  - check: <что проверено>
    evidence: <результат>
open_risks:
  - <риск или none>
constraints:
  - <что следующий владелец не должен нарушить>
next_owner: <роль>
next_action: <одно конкретное действие>
stop_conditions:
  - <когда нельзя продолжать автономно>
```

Версию схемы выбирать одну для всей системы. При наличии существующей канонической схемы расширять её совместимо, а не создавать конкурирующий формат.
